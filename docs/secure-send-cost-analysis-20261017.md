## 3. 既存DBで測れるもの・測れないもの

集計専用SQLを同じ分析ブランチのcost-analysis-aggregate-readonly.sqlに用意した。未実行。read-only transaction、30秒timeout、月単位の集計のみ。DB負荷を確認して実行する。

- 送信：作成グループ数とアップロード完了ファイル数は分ける。notified_atは通知権取得であり配送成功数ではない。
- サイズ：DBのsize_bytesはクライアント申告。実転送量ではなく申告サイズの統計と明記する。
- ダウンロード：auditのdownloadedは署名URL発行。GET完了件数・実送信bytesはGCSメトリクス/既存アクセスログが必要。現在のclean状態×累計回数から過去月の実DL量を逆算しない。
- OTP：auditのotp_requestedはSMTP呼出後の記録。発行行数はSMTP失敗も混ざり得る。受信箱への配送成功数ではない。
- scan：scanned_at-uploaded_atは待ち時間・GCS読込・プロセス起動込み。純ClamAV時間、並行数ピークはDBだけでは復元しない。
- 保持：lifecycle21日は平均保存期間の実測ではない。物理削除日時・soft delete課金・バックアップ保持は別に取得する。
- 指標が過去に記録されていなければ未確認のまま残し、新規計測は別実装として承認範囲を確認する。

## 9. Secure Guardとセット割引

Secure Guardの5,000円＋300円/端末を本モデルの収益へ足していない。Secure Send独立の差引額から割引余力を評価する。

売上50%配分・目標差引率20%を維持する仮定では、標準100社で全プランの割引余力は0円。標準500社の算術上限は約113/580/515円/社月、1,000社では約196/664/591円。増強費・営業費等を除いた上限なので、そのままセット割引には使わない。Guard側利益は未取得で、両サービス合算利益と契約上の配分対象を確認してから正式判断する。

## 10. 追加の重要確認事項

1. scanの月額・billable time・課金方式、実scan時間、起動頻度、同期待ち・queue時間。常時ウォームだけで定義更新が継続するとは限らず、entrypointは起動時freshclamのみ。更新運用は商用リスクとして統括確認。
2. 既存OTP処理はverified_atがあれば入力コード検証より前に成功を返す分岐がある。今回変更しない。商用化前の認証回帰と修正判断が必要で、既存機能を安全確認済みとは扱わない。
3. DB backup/HA/復旧、GCS soft delete/versioning、SMTP制限・到達性、監視・夜間対応責任は未確認。
4. 開発費・営業費・初期設定/移行・利用者教育・事故対応の原価と、紹介/販売/一次対応で配分先が担う範囲を統括で定義。単に売上比率だけを決めない。

## 11. 統括へ戻す判断事項と取得依頼

正式価格・人数境界・配分対象基本料・配分率・上限超過時の挙動・提供対象・SLAはすべて保留。実績が揃うまで、PIRA提案では価格候補と限定パイロット条件として扱う。

取得を再開する最小資料は、(a)2026年7〜9月＋10月部分月のSKU別請求export（project/service/resource、使用量、cost、credits、currency）、(b)3サービスの非秘密構成とメトリクス、(c)バケット設定と月間bytes、(d)上記匿名SQL結果、(e)Secure Send運用時間記録。共有DB/LB費用は資源利用根拠が揃うまで実配賦しない。請求exportには他サービスの詳細が含まれるため、必要列と対象projectに限定する。
