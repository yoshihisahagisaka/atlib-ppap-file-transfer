# PPAP回避ファイル送信システム デプロイ手順書

対象プロジェクト: `msp-zabbix`(プロジェクト番号 `135863453696`) / リージョン: `asia-northeast1`

## 構成(2026-08-19時点・稼働中)

- **upload-service**(社内・IAP配下): `https://ppap-upload.atlib.jp`。アップロード受付・署名付きURL発行・ウイルススキャンの同期呼び出し・監査ログ閲覧(`/audit.html`)。
- **download-service**(社外・公開): `https://files.atlib.jp`。OTP認証・ダウンロード。

### アクセス制御(2段階)

upload-serviceは1つのCloud Runサービスだが、URL Map(`msp-iap-urlmap`)のパスルールで**2つのbackend serviceに振り分け**、それぞれ別のIAPポリシーを適用している(同一Serverless NEGを両backend serviceで共有):

| パス | backend service | 許可グループ |
|---|---|---|
| それ以外全て(送信フォーム・送信履歴等) | `ppap-upload-bes` | `atl_info@atlib.jp` |
| `/audit.html`, `/audit.js`, `/api/audit-logs*` | `ppap-audit-bes` | `director@atlib.jp` |

backend serviceが違うとIAPが発行するJWTの`audience`も変わるため、アプリ側(`IAP_AUDIENCE`環境変数)は両方のaudienceをカンマ区切りで受け付ける(`src/middleware/iapAuth.ts`)。`msp-staff@atlib.jp`は当初使っていたが、`atl_info@atlib.jp`に完全に置き換えた(msp-staffでは本ツールにアクセスできない)。
- **ppap-virus-scan**(Cloud Run service、`--min-instances=1`で常時ウォーム): ClamAVスキャン。upload-serviceの`/complete`から**同期呼び出し**される(GoogleAuthのOIDC IDトークンによるサービス間認証)。スキャンがclean判定になった時点でこのサービス自身が受信者への通知メールを送信する。
- 既存Cloud SQLインスタンス`msp-customer-portal-db`に相乗り(`ppap_transfer`データベース)。
- 専用GCSバケット`atlib-ppap-file-transfer`(非公開・21日lifecycle・CORS設定済み)。

**設計上の重要なポイント**: 受信者への通知メールは、ウイルススキャンが完了(clean判定)して初めて送信される。アップロード完了時点では送らない。これにより受信者がスキャン待ちの画面を目にすることはなく、待ちは送信者側(社内スタッフ、アップロード完了までスピナー表示)に寄せている。

**Eventarcは使用しない**(意図的に廃止): 当初はGCSアップロードをEventarcでトリガーする非同期スキャンJobとして設計したが、(1) 安定版gcloudはCloud Run Jobを直接の宛先にできない、(2) 同期呼び出し方式に変更した後もEventarcを「保険」として残したところ、同期呼び出しとEventarc経由呼び出しが同時に発火し、スキャンサービスへの同時アクセスでコールドスタート競合が発生し、かつEventarc経由の呼び出しは`downloadToken`を持たないため通知メールが送られずに完了してしまう不具合が発生した。そのため`ppap-scan-trigger`は削除し、upload-serviceからの同期呼び出しのみを正とする構成にしている。

### 各サービスのビルド・デプロイ

イメージは`cloudbuild.upload.yaml` / `cloudbuild.download.yaml` / `cloudbuild.scan.yaml`(いずれもDockerfileが複数あるため`gcloud run deploy --source`の素の`--dockerfile`指定はできず、`gcloud builds submit --config=...`でビルドしてから`--image`でデプロイする2段階方式)。

```bash
# download-service
gcloud builds submit --config=cloudbuild.download.yaml .
gcloud run deploy ppap-download-service --image=asia-northeast1-docker.pkg.dev/msp-zabbix/cloud-run-source-deploy/ppap-download-service \

#  表示されたCNAME(files→ghs.googlehosted.com)をDNSに追加)

# ppap-virus-scan (先にデプロイしてURLを確定させる。upload-serviceがこのURLを呼ぶため)

  --region=asia-northeast1 --no-allow-unauthenticated --memory=2Gi --min-instances=1 \
  --add-cloudsql-instances=msp-zabbix:asia-northeast1:msp-customer-portal-db \
```

### 既存IAP LBへの統合(ppap-upload.atlib.jp)

既存の静的IP `136.68.254.85` / `msp-iap-urlmap` / `msp-iap-https-proxy` に、`cashflow.atlib.jp`追加時と同じパターンで相乗りする。

```bash
gcloud compute network-endpoint-groups create ppap-upload-neg --region=asia-northeast1 --network-endpoint-type=serverless --cloud-run-service=ppap-upload-service
gcloud compute backend-services create ppap-upload-bes --global --load-balancing-scheme=EXTERNAL_MANAGED
gcloud compute backend-services add-backend ppap-upload-bes --global --network-endpoint-group=ppap-upload-neg --network-endpoint-group-region=asia-northeast1
gcloud compute url-maps add-path-matcher msp-iap-urlmap --path-matcher-name=ppap-upload-matcher --new-hosts=ppap-upload.atlib.jp --default-service=ppap-upload-bes

# DNSで ppap-upload.atlib.jp → A → 136.68.254.85 を先に登録してから証明書発行
gcloud compute ssl-certificates create ppap-upload-cert --domains=ppap-upload.atlib.jp --global
gcloud compute target-https-proxies update msp-iap-https-proxy --ssl-certificates=msp-iap-cert-v2,atlib-cashflow-cert,ppap-upload-cert

gcloud compute backend-services update ppap-upload-bes --global --iap=enabled
# IAP OAuthクライアントは既存のもの(msp-iap-client)を流用する。新規発行すると失敗する
# (「Error: Forbidden」表示になった実績あり。既存クライアントのID/シークレットは
#  `gcloud iap oauth-clients list projects/135863453696/brands/135863453696` で取得できる)
gcloud compute backend-services update ppap-upload-bes --global --iap=enabled,oauth2-client-id=<既存msp-iap-clientのID>,oauth2-client-secret=<同シークレット>

gcloud iap web add-iam-policy-binding --resource-type=backend-services --service=ppap-upload-bes \
  --member="group:msp-staff@atlib.jp" --role=roles/iap.httpsResourceAccessor

# IAP_AUDIENCEを確定させて再デプロイ
BID=$(gcloud compute backend-services describe ppap-upload-bes --global --format='value(id)')
gcloud run services update ppap-upload-service --region=asia-northeast1 \
  --update-env-vars="IAP_AUDIENCE=/projects/135863453696/global/backendServices/${BID}"
```

## 既知のトラブルシューティング事例

- **「Error: Forbidden / Your client does not have permission」**: 2パターンあった。①IAP有効化時にOAuthクライアントを指定しなかった場合(既存クライアントを明示的に指定する) ②`ppap-upload-service`を`--no-allow-unauthenticated`にした場合(Cloud Run自体の認証層。`--allow-unauthenticated`にする)。
- **DBパスワード認証エラー(`password authentication failed for user "ppap_app"`)**: PowerShellで`$pw | gcloud secrets create ... --data-file=-`のようにパイプ経由で渡すと末尾に改行が混入することがある。`[System.IO.File]::WriteAllText()`でファイルに書き出してから`--data-file=<path>`で渡すこと。
- **ClamAVコンテナがOOM Kill**: `--memory=1Gi`でも不足。`--memory=2Gi`必須。
- **同期スキャン呼び出しが503**: コールドスタートが原因。`--min-instances=1`で常時ウォームにする(月額+$15〜20程度)。
- **`gcloud run domain-mappings create --region=...`が`unrecognized arguments`**: フルマネージドCloud Runでは`gcloud beta run domain-mappings`が必要。betaコンポーネント導入に管理者権限が必要な場合はCloud Consoleの「Cloud Run > ドメイン マッピング」から行う。
- **`/d/<token>`ページで静的アセット(JS/画像)が404、画面が固まる**: HTML内の相対パス(`src="download.js"`等)は`/d/<token>`という深いパスから見ると誤った場所に解決される。`/download.js`のように絶対パスにすること。

## 動作確認

1. `https://ppap-upload.atlib.jp` にWorkspaceアカウントでアクセスできること(IAP経由)。
2. テストファイルをアップロード→「送信」ボタンがスキャン完了まで待つ(スピナー表示)→完了後に受信者へ通知メールが届くことを確認する(送信直後には届かないこと)。
3. `https://files.atlib.jp/d/<token>` でOTPリクエスト→メールでコード受信→ダウンロード成功まで確認。待ち画面を経由しないこと。
4. わざと [EICARテストファイル](https://www.eicar.org/) をアップロードし、ウイルス検出→ファイル削除→送信者への通知メールが届くことを確認。
5. Cloud SQLの `audit_logs` テーブルに一連のイベント(created, uploaded, scan_clean/scan_infected, otp_requested, otp_verified, downloaded)が記録されていることを確認。
